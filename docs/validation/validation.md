작은 편집을 반복하는 동안에는 변경한 package와 호출자, fixture·script에 해당하는 검사를 명시적으로 골라 먼저 실행한다. Go import 역관계만으로 범위를 확정하지 않는다. 소스 직접 읽기, subprocess 실행, embed, testdata, build tag·host 조건과 공용 계약의 영향을 확인하고 불명확하면 아래 전체 local foundation 및 해당 native/통합 검사로 확대한다. 자동 path-filter로 필수 CI를 생략하지 않는다.

예를 들어 scheduler 정책만 편집하는 첫 단계는 `go test ./src/internal/foundation -run '^TestWorkflow' -count=1 -v -timeout 300s`로 시작할 수 있다. producer·margin 계약까지 바뀌면 `go test ./src/dev/ci-gate -count=1 -v -timeout 300s`와 관련 호출자 검사를 추가한다. 이는 개발 중 빠른 피드백이며 최종 후보의 foundation·native·qualification을 대체하지 않는다. 같은 입력에서 완료된 검사를 새 변경이나 실패 근거 없이 반복하지 않되, 최종 PR 후보와 actual main의 기존 필수 검사는 모두 실행한다. 작은 수정마다 push하는 대신 검토 가능한 변경 단위를 완성한 뒤 PR CI를 실행한다.

**PR light 모드 (#252).** 반복 수정 중인 PR에 label `ci:light`를 붙이면 그 PR의 run은 foundation 세 개만 실행한다. 비 heavy `mode` job(PR code checkout 없음, 권한 `pull-requests: read`·`actions: read`)이 실행 시점의 현재 label을 API로 조회하고, `native-prepare`만 그 결과로 시작 여부를 정한다. route·large API·qualification은 기존 의존 관계로 함께 skip된다. 조회 실패와 PR이 아닌 event는 full이다. `mode` job 자체가 실패하면 foundation과 heavy job이 실행되지 않고 integration gate가 실패한다. integration gate는 `always()`와 여섯 producer `needs`를 유지하므로 light run은 필수 check를 통과할 수 없다. label 이벤트는 trigger로 쓰지 않는다. skip된 필수 job이 같은 head에 skipped check를 남기는 것과 불필요한 run을 막기 위해서다(도입 당시의 single queue에서는 pending run을 밀어내는 문제도 있었다). 최종 후보는 label을 제거한 뒤 그 head의 run 전체를 다시 실행하거나(새 attempt), label 없이 다음 push를 한다. 이 전체 재실행은 의도적으로 생략한 검증을 완성하는 단계다. 아래 무변경 재시도 예외가 아니며, full run의 실제 실패를 label 조작으로 재시도하는 근거도 아니다. 보장 범위는 "최종 후보 head에 대한 full 검증 성공"이며 label 부재 자체를 병합 조건으로 만들지 않는다. 같은 PR에 새 head를 push하면 이전 head의 PR run은 진행 중이든 대기 중(pending/queued)이든 취소한다. 대상은 같은 repository·Foundation workflow·PR·branch의 `pull_request` run이고, run의 head가 현재 PR head가 아닐 때만이다. 취소 직전에 현재 head와 대상 run을 다시 확인하고, 요청 뒤 terminal 상태를 확인한다. main·schedule·dispatch run은 취소하지 않는다.

**중복 nightly 생략 (#257).** schedule run에서 `mode` job은 같은 commit의 Foundation run 가운데 최근 24시간 안에 끝난 성공한 main `push`·`workflow_dispatch` run이 있는지 API로 조회한다. 있으면 foundation이 skip되고 나머지 producer는 의존 관계로, 두 진단은 `needs.foundation.result != 'skipped'` 조건으로, integration gate는 schedule event에서 foundation이 skip된 경우에만 skip된다. 그 결과 `mode`만 실행되고 run은 성공으로 끝난다. 생략됐든 아니든 nightly의 성공은 다음 생략 근거가 되지 않는다. 조회 시점의 최근 24시간에 적격 push·dispatch 성공이 없으면 전체 검사를 시도한다. 예를 들어 전날 늦게 끝난 push 검사로 오늘 nightly가 생략되면 다음 전체 nightly는 그다음 날이므로, 같은 commit의 전체 검사 간격은 24시간을 넘을 수 있다. 조회 실패는 전체 run이다. schedule이 아닌 event에는 중복 생략을 적용하지 않으며 위 PR light 정책은 그대로다. pull_request·push run에서는 gate가 skip될 수 없다(`TestWorkflowNightlyDuplicatePolicy`). 생략된 run에는 margin 보고서가 없어 margin history에서 `NO_LATEST_ATTEMPT_REPORT`로 제외된다. 다만 보고서 확인 전에 최신 completed run 60개를 고르므로 생략된 run도 그 한도를 차지해, 같은 구성 표본 n≥20 도달이 늦어질 수 있다. 2026-10-16~21의 nightly 6회는 모두 이미 성공한 push run과 같은 commit을 다시 검사했다(한 번 약 77분).

**공유 lane의 queue (#252).** Foundation의 workflow 수준 concurrency는 group `tsgk-campaign-heavy`, `cancel-in-progress: false`, `queue: max` 하나다(`TestWorkflowConcurrencyPolicy`). 기본 single queue에서는 새로 queue된 run이 기존 pending run을 취소했고, 실제로 main post-merge run이 다른 PR run에 밀려 job 없이 취소된 적이 있다(run 39360820279, `eb9480f`). `queue: max`는 pending을 최대 100개까지 유지한다. 가득 차면 이후 run은 main이라도 취소되고, FIFO가 원칙이지만 순서는 보장되지 않으며 대기 시간의 상한도 없다. 따라서 병합 뒤 main CI 확인과 낡은 PR run 취소 절차는 그대로 유지한다. 도입 직후에는 이전 workflow revision의 run이나 그 재실행이 single 정책으로 같은 group에 남을 수 있어, 정책이 섞인 동안의 pending 보존을 가정하지 않는다. group 이름은 바꾸지 않는다. 바꾸면 이전 group과 새 group의 run이 동시에 실행되어 heavy 폭 3을 넘을 수 있다.

기록에는 실제 base/head, dirty 입력과 실행 문맥, 명령·선택 범위·결과를 남긴다. 미선택 범위는 `NOT_RUN`이며 과거 PASS는 원래 commit·문맥·run/attempt가 있는 역사적 근거로만 참조한다. 계획 출력·변경 없음·테스트 없는 package의 build를 새 테스트 PASS로 표시하지 않는다. `-count=1`을 유지해 테스트 결과 캐시로 새 실행을 대신하지 않고, 계산 재사용은 build identity와 cold 검사를 보존하는 범위에서 검토한다.

## #215 출력 소유권 검증

`TestPublishKeepsParentIdentity`는 검사 후 최종 게시 전 output parent pathname을 다른 directory로 교체하는 결정적 barrier를 사용한다. 보관한 parent에만 게시·정리하고 대체 directory의 기존 bytes를 보존해야 한다. Windows에서 열린 handle이 rename을 거부한 경우에도 그 실제 거부를 확인한다. `TestDirectoryReplacementDuringScan`은 child lookup 사이의 보통 directory·내부 alias·외부 alias 교체를 거부한다. `TestQualifyRechecksEveryHostBeforePublish`는 분석 후 2·3번째 host pathname을 바꾸어 최종 검사가 모든 host에 적용되는지 확인한다. cleanup 실패는 성공한 publication 사실을 보존하면서 오류로 보고해야 한다.

native의 두 process가 같은 output을 동시에 선점하는 시험은 하나만 directory와 member를 만들고 다른 하나는 `OUTPUT_EXISTS`에 해당하는 충돌로 종료해야 한다. 기존 output·member bytes와 배타 child 생성을 검사하고, 획득한 output handle 뒤의 pathname 교체가 member 쓰기를 대체 directory로 돌리지 못하는지 확인한다. Windows 생성 handle은 native 생성과 Go root 연결 구간에 유지하며, reserved/ADS 이름·기존 alias와의 충돌을 거부한다. `Mkdir`와 첫 handle 획득 사이의 Linux·macOS 공백은 별도 미완료 항목이며 이 시험의 PASS로 해결했다고 기록하지 않는다.

Windows foundation의 별도 `hosted Windows subst output boundary (#215)` step만 `TSGK_HOSTED_SUBST_TEST=1`로 `TestHostedSubstMembership`을 실행한다. GitHub-hosted Windows 문맥을 확인하기 전에 mapping을 만들지 않으며, 개발 host 거부는 별도 subprocess negative control로 확인한다. unused drive의 실제 `subst.exe` mapping과 target을 확인하고 input 하위 mapping 거부·outside mapping 허용·원 bytes 보존·partial 부재·mapping 제거를 검사한다. 제거에는 예상 target에 대한 `DefineDosDevice` exact-match removal을 사용하고 다른 target을 주면 기존 mapping이 보존되는 대조도 실행한다. mapping 소유권이나 제거를 확인하지 못하면 fixture를 보존하고 후속 mapping을 중단하여 실패한다. workflow는 정확한 test의 Go JSON pass와 inside·outside·두 제거·두 다른-target 보존 witness를 요구한다. `TestHostedSubstEvidenceGuard`는 이 event 검사 자체를 정상·skip·무선택·실패·witness 누락 fixture로 검사하며 실제 mapping 근거로 세지 않는다. skip·mapping 생성 실패·timeout은 실제 subst 검증 PASS가 아니다. 개발 host에서는 실제 mapping을 실행하지 않는다. 기존 isolated Linux bind-mount 검사는 유지한다.

## CI and evidence

필수 통합 판정은 `foundation (windows-2025)`, `foundation (ubuntu-24.04)`, `foundation (macos-15)`와 `integration gate`다. 원격 ruleset의 required check 등록은 workflow 도입과 별도 효과이며, 실제 등록 전에는 자동 강제가 완료됐다고 기록하지 않는다. Go version/OS/arch, 실제 checkout SHA와 runner ImageOS/ImageVersion을 확인한다. image version을 고정했다는 주장은 하지 않는다. tests·vet·build·policy·CGO dependency 검사가 모두 성공해야 한다. skipped·cancelled·missing은 PASS가 아니다. checkout은 event의 `github.sha`와 일치해야 한다. PR은 head와 base의 synthetic merge를 검사한다. PR head·synthetic checkout·actual merge commit을 구분하고 merge 뒤 실제 commit을 다시 검증한다.

`integration-gate`는 foundation·native-prepare·native-routes·native-routes-macos·large-api·qualification을 직접 `needs`로 받고 `always()`로 실행하는 15분 상한의 offline gate다(중복 nightly의 skip은 위 #257 예외). 여섯 producer 결과가 정확히 success여야 한다. Windows/Linux matrix와 Mac singleton의 성공 여부를 모두 검사하며, 실패·누락·skipped·cancelled는 통합 성공이 아니다. [helper](../../src/dev/ci-gate/main.go)는 workflow가 기록한 현재 repo/workflow/run/attempt/event/SHA와 PR head·실제 checkout을 기대값으로 사용한다. PR head를 synthetic checkout 대신 쓰거나 이전 attempt의 artifact를 가져오지 않는다. 현재 run API에서 정확한 이름 다섯 개를 고유 ID로 골라 expired·누락·중복을 거부하고, 공식 ZIP digest/size를 실제 다운로드 bytes와 비교한 뒤에만 해제한다. HTTP transport는 PowerShell 7 `fetch.ps1`·`http.ps1`에만 있다. 기존 Go network import 금지 검사는 유지하며 Go helper는 metadata plan·ZIP unpack·verify 모두 offline이다. API token은 fetch step에만 있고 Go subprocess 환경에서 제거하며 redirect에 전달하지 않는다. 일시적인 transport 실패(연결 오류, 끊긴 응답, 500·502·503·504)는 같은 요청을 최대 세 번까지 기존 deadline 안에서 시도한다(#275). 시도마다 GitHub endpoint에서 다시 시작하므로 token은 첫 hop에만 간다. 이번 시도가 만든 부분 파일만 지우고, 이미 있던 출력은 바꾸지 않는다. 그 밖의 상태·redirect·크기 위반과 deadline은 다시 시도하지 않는다. 완결된 artifact 목록에 현재 attempt의 필수 artifact가 없기만 하면, GitHub 목록 반영 지연으로 보고 30초 간격으로 최대 두 번 더 목록을 받는다(`ci-gate plan` exit 3). 같은 이름의 이전 attempt artifact만 있으면 부분 재실행으로 보고, run 전체를 다시 실행하라는 오류로 바로 실패한다. margin config artifact도 같다. 어느 경우에도 이전 attempt artifact를 받아들이지 않는다. fetch 실패는 verify 실행을 막는다. verify step은 credential 없이 로컬 파일만 읽는다.

ZIP은 현재 hosted artifact가 쓰는 single-disk·comment-free classic 형식만 받는다. ZIP64와 확장 형식은 거부한다. 압축 100 MiB, central directory 8 MiB, 실제 entry 수·경로·파일당 64 MiB와 기존 qualification host의 10,000개 파일·576 MiB(#217) 상한을 적용한다. case 충돌, 경로 탈출·ADS·특수 entry, 실제 해제 크기 초과를 거부한다. parsing·copy에 취소를 연결한다. 다운로드 receipt와 ZIP·해제 파일의 hash를 다시 대조하며, receipt는 별도 서명이 아니다. 이 흐름은 caller 소유의 변경되지 않은 hosted runner temp를 전제로 하며 적대적 동시 디렉터리 교체에 대한 sandbox가 아니다. artifact의 코드·명령은 실행하지 않는다.

원본 세 host를 현재 inventory로 `kit.Qualify`하여 정확한 78개 고유 cell과 inventory의 모든 obligation, 내부 completeness·mechanism gate·세 플랫폼 SUPPORTED·findings 0을 확인한다. hosted qualification JSON과 재집계 bytes가 같아야 한다. large API는 동일 run identity, 고정 fixture·registry·auditor source와 정상 build, small full oracle 네 개, large baseline 세 개, node 0부터 마지막까지 gap·중복·순서 역전 없는 1,000,000-node page, child 합계 nodes−1·검사 수·process 한도, 정확한 fault 아홉 개와 resource control 하나를 검사한다. large baseline은 field count를 선언하지 않는 native r1이다. 네 개의 small r2 full oracle에서 field inventory 일치를 확인하고 모든 정상 page·fault에 결속하며, large r1 producer의 ABI를 같은 build의 small producer와 대조한다. 현재 후보는 r4 단일 session large validation과 원본 resource capture를 요구한다. 형식·필수 key·상한·고정 요청·typed 응답의 owning 계약은 [tree/protocol](../specs/tree-and-adapter-protocol.md)이며 live caller와 offline gate가 공용 `largeaudit.CheckResource`를 사용한다. gate는 정상 baseline producer ABI와도 대조하며 원본 frame 없는 r1으로 fallback하지 않는다. frame/hash는 저장된 일관성 근거이고 producer 정직성이나 OS 집행·정리의 독립 증명이 아니므로 기존 live 시험을 유지한다. 공용 [receipt decoder](../../src/internal/largeaudit/receipt.go)는 live audit와 offline gate가 함께 쓴다. 성공한 gate의 `result.json`과 run identity는 `integration-gate-<run>-<attempt>`에 보존한다. 실패는 action log와 nonzero exit로 남으며 누락된 결과 파일을 성공으로 해석하지 않는다. 음성 대조는 producer 실패/skip/cancel/누락, 다른 cohort/SHA, 누락·중복 cell/obligation, 내부 gate 실패, 변조·누락 artifact, 위험한 ZIP, page coverage·fault·resource 누락을 거부해야 한다.

### #214 시간 여유 관측

[margin helper](../../src/dev/ci-gate/margin.go)는 필수 producer 9개 expanded job의 실제 시작·종료 시간, 명시적 timeout이 있는 step 7개, large audit의 정상 page wall 최댓값 하나를 기록한다. 대상은 foundation 3개, native-prepare 1개, native-routes 3개, large-api 1개, qualification 1개다. step은 foundation의 반복 cancellation 3개·Linux bind mount와 tree 정리 각 1개·Linux sanitizer 1개·Windows large audit 1개다. job과 step은 원본 GitHub attempt jobs API의 completed/success·run/attempt/head SHA와 timestamp를 확인하며, page wall은 현재 raw artifact를 통과한 core 결과를 사용한다. 진단 3개와 아직 실행 중인 integration gate, package별 go test timeout(native 420초, 나머지 300초)은 이 측정 집합에 포함하지 않는다. integration gate 결과의 `large`는 같은 memory metric으로 측정한 최대 peak와 그 fixture, hard 한도, 남은 여유(`memory_metric`·`memory_peak_source`·`memory_limit_bytes`·`memory_headroom_bytes`)를 관측값으로만 기록하며, 서로 다른 metric이 섞이면 거부한다. 이 값은 정상 audit page·session process의 peak만 집계하며 baseline·full oracle·fault·resource control·compile·orchestration process를 제외하므로 large API job 전체나 host의 남은 memory를 뜻하지 않는다. memory·출력·저장 한도는 기존 hard validation을 유지하며 새 70% gate로 승격하지 않는다.

구성 key는 go.mod/go.sum·workflow·src 정규파일의 bytes/hash, job/OS/arch, runner OS/arch와 정확한 ImageOS/ImageVersion, Go 버전, 실제 선택한 C compiler의 SHA/bytes(compiler를 쓰는 job), metric과 적용 한도를 결속한다. runtime·grammar·fixture와 concurrency·argv·define 정책은 이 source 집합의 고정 등록부와 실행 script에 포함된다. 문서·run/attempt/head·일회성 build 경로는 key에 넣지 않고 provenance로 보존한다. native host/large의 run identity 및 실제 compiler는 이미 검증된 artifact와도 대조한다. foundation 등 compiler 사용 job은 현재 선택 파일을 기록하며, compiler를 쓰지 않는 prepare/qualification은 명시적 null이다. 같은 ImageVersion에서도 물리적 runner가 같다고 주장하지 않는다. 환경·source가 자주 바뀌면 동일 구성 20개 확보 시점을 보장할 수 없다.

현재 run의 유효한 metric 하나와 과거 각 run 자체의 관측만 세며, 35 pages나 다른 attempt를 별도 표본으로 세지 않는다. key가 다른 표본은 합치지 않는다. 과거 보고서는 기록 당시의 상한으로 검증한다. 상한이 현재와 다르면 key도 달라 다른 구성의 표본이 되고, 현재 metric의 표본 수에 더하지 않는다. 그래서 상한을 바꾼 뒤에도 history로 선택된 옛 상한 보고서(최근 30일, completed 최대 60개)가 오류가 되지 않는다(#260). source에는 workflow와 상한표가 함께 들어가므로, 현재와 같은 source를 주장하면서 다른 상한을 기록한 과거 보고서는 모순으로 거부한다. 현재 보고서는 현재 상한과 정확히 같아야 한다. Go 버전도 같다. 보고서 자신의 run과 측정 configuration마다 Go 버전을 검사한다. 현재 보고서는 고정 toolchain `go1.27.2`만 받고, 과거 보고서는 이전 고정 값 `go1.27.1`도 받는다. Go 버전은 key에 들어가므로 이전 toolchain의 표본은 따로 센다(#261). 현재를 포함해 n<20은 `INSUFFICIENT_SAMPLE` 경고다. 사용률이 70%를 초과하면 추가 경고하며, n≥20에서 현재 사용률이 70%를 초과하면 required integration gate가 실패한다. 정확히 70%는 통과한다. 정수 비율로 판정하며 반올림한 표시값을 사용하지 않는다. GitHub API의 초 단위 timestamp가 같은 정상 완료 step은 관측값 0ms로 기록하며, 실제 실행 시간이 정확히 0이라는 뜻은 아니다. 시작/종료 값은 모두 있어야 하고 종료 시각 역전은 거부한다. timestamp·metric·필수 필드의 누락/null/파싱 실패, 분모 0, 중복·충돌·불완전 수집은 표본 부족으로 바꾸지 않고 실패한다. timeout 뒤 정리 시간이 포함된 유효한 job 관측이 100%를 넘는 것도 보존하며, margin 판정과 기존 execution timeout 집행을 구분한다.

[수집기](../../src/dev/ci-gate/margin-fetch.ps1)는 같은 repository/Foundation/main의 최근 30일 run을 먼저 조회한다. PR·fork·다른 workflow의 보고서는 history로 사용하지 않는다. 최대 1,000개 run의 pagination을 완결하고, cutoff를 생성 시각 window의 상한으로 삼고, 각 API 응답을 관측했을 때 completed인 최신 60개 run을 선택한다. 이 응답은 attempt 상태의 원자적인 과거 snapshot이 아니다. API가 알려 준 최신 attempt의 정확한 report만 고르며 이전 성공 attempt로 돌아가지 않는다. 아직 미완료인 최신 attempt, report 도입 전 run, 만료 report는 현재 cutoff의 제외 사유로 남긴다. 조회 상한/누락 page는 `HISTORY_WINDOW_INCOMPLETE` 실패다. 과거 report의 Samples/State 집계를 다시 수입하지 않으며 run ID 중복을 거부한다.

현재 구성 artifact는 producer마다 고유 이름으로 7일, 작은 `ci-margin-<run>-<attempt>`의 `margin.json`은 30일 보존한다. report에는 자체 관측·구성·core result SHA·cutoff·제외 사유가 들어간다. 공식 API run/attempt/event/head, artifact ID·공식 ZIP digest/size와 단일 정규파일을 검증한다. compressed/expanded report는 각각 256 KiB 상한이며 기존 안전한 ZIP reader를 재사용한다. HTTP는 기존 token scope를 유지한다. 기존 core download의 365초 deadline과 unpack 한도는 유지하고, 새 margin 수집 전체에는 별도 120초 deadline을 적용한다. Jobs API는 이 gate가 기다린 완료 job을 늦게 반영할 수 있으므로, 수집기는 같은 deadline 안에서 측정 대상 job 9개·step 7개가 모두 completed와 시작·종료 시각을 가질 때까지 현재 attempt의 jobs snapshot을 15초 간격으로 최대 4번 새로 받는다(`ci-gate margin-settled`). 최종 판정은 마지막 snapshot 하나로 하며, 그래도 미완료면 기존 검사가 실패한다. 판정 기준과 deadline을 완화하지 않으므로 이보다 긴 API 지연은 해결하지 못한다. job의 기존 15분 timeout과 native 한도는 늘리지 않으며 추가 권한이나 job을 만들지 않는다. 현재 core ZIP 5개와 history는 별도 root다. 유효한 20번째 초과 관측은 report를 먼저 쓴 뒤 실패하고 always upload한다.

7일 뒤 큰 artifact가 만료되면 30일 history는 trusted main producer가 당시 검증해 보존한 현재 관측 결과다. ZIP digest는 전달 무결성을 확인하며 사라진 raw artifact를 다시 실행·재검증하거나 별도 서명으로 신뢰를 승격하지 않는다. 이 history는 현재 후보의 `NEW_RUN` qualification을 대체하지 않는다. 실제 동일 구성 20개를 모았다는 운영 근거와 19/20 음성 대조의 성공을 구분한다.

동일 run build 공유는 [CLI의 build-cache 계약](../specs/cli-and-profile.md#incremental--oracle-record---build-cache-dir-214)을 따른다. native route helper는 새 run 전용 cache를 사용하되 모든 native case를 다시 실행한다. `TestBuildCache`·`TestBuildCacheRecordBounds`와 CLI의 `build-cache` 사례는 cold/hit·새 build 소유권·원래 compilation provenance·잘못된 기록/argv·실행 파일 변조·정상/fault 분리·입력/도구 재검증을 검사한다. compiler process 감소와 시간 관측은 단일 owned grammar 표본이며 전체 CI 속도 보장이 아니다. 큰 artifact의 work/cache는 qualification host 파일 집합에 넣지 않는다.

대용량 단일 process session과 동일 구성 20개 운영 표본은 #214의 후속 범위다. 기존 resource artifact의 원본 실패 frame 부재와 개선안은 [offline 검증 분석](../reports/issue-214-resource-offline-verification.md)에 기록한다. margin 구현이 그 한계를 해결하거나 timeout·메모리·fixture를 완화하지 않는다.

### Frame·cancellation 시험 (#65)

`TestFrameStatusMapping`과 `TestFrameEscapedStdoutHolder`는 helper readiness를 기다리고, 시험 전용 frame timer hook으로 선택한 frame의 `.at` handshake 뒤에만 watchdog을 만료시킨다. 다른 종료 원인을 검사하는 사례에서는 frame timer가 그 원인과 경쟁하지 않는다. timer에 넘긴 `FrameWall + FrameGrace`, 기존 상태·응답·종료 이유·cleanup·15초 전체 batch 단언은 유지한다. `TestFrameWatchdogRealTimer`는 실제 timer 경로에서 readiness 뒤 첫 frame을 멈춰 watchdog과 cleanup을 확인한다. native `TestLimitsAndCancellation/cancellation`은 이미 마지막 request byte를 보류한 뒤 caller context를 취소하므로 parse 속도와 경쟁하지 않는다. runner/driver 운영 상한과 기대값은 바꾸지 않는다.

### Native runtime patch 검증 (#105)

[runtime patch 정책과 identity](../provenance/upstream-sources.md#native-runtime의-field-조회-patch-105)는 runtime manifest가 소유한다. `prepare-routes.ps1`의 `-LocalRuntime`은 고정 기반 commit의 **원본** source를 받는다. 준비 과정은 원본 target hash·bytes, local patch subject hash·bytes, literal 문맥의 정확한 occurrence 수, 적용 후 83개 closure hash를 확인한다. 이미 patch된 source를 원본 대신 넣거나 hash 검사를 우회하지 않는다. build의 `RUNTIME_MISMATCH` 검사는 적용 후 closure를 그대로 강제한다.

patch 변경은 원본과 후보를 별도 준비한 같은 host에서 `run-routes.ps1 -Large -Oracle`로 비교한다. API findings가 줄고 모든 기존 사례의 tree·incremental·query·사실 결과와 `requirement_results`가 유지되어야 한다. 시간과 producer identity는 host 관측으로 구분한다. foundation의 `TestRuntimePatch`는 원본·subject·출력 hash와 literal 문맥의 실패를 검사한다. native의 `TestRuntimeFieldOwnership`·`TestRuntimeFieldRecoveryAndShadow`·`TestRuntimeFieldByName`은 alias/hidden 상속·가까운 field shadow·ERROR·extra 경계와 negated-field capture, by-name locator의 byte 범위·unknown field null을 독립 기대값으로 검사한다. 원본 runtime mutant가 의도한 field 조회·query 이유로 실패해야 한다. 독립 보안 관점 리뷰와 실제 세 OS CI에서 qualification artifact의 `support_claim`·`platform_claims` 및 감소한 `api_findings`를 직접 확인한 뒤 병합한다. foundation은 `go list ./src/...`의 전체 패키지를 native와 나머지로 나누어 모두 실행한다. 나머지 패키지의 기존 병렬 실행 뒤에 native를 별도로 실행하여, native의 실제 C 컴파일과 다른 테스트 패키지의 컴파일이 같은 host에서 경합하는 것을 줄인다. native 패키지 누락이나 열거 실패는 거부한다. 패키지 내부의 `t.Parallel`과 전체 테스트 범위는 유지한다. go test timeout은 나머지 패키지 300초, native 420초다(#260). native는 Windows에서 237–267초로 이전 300초의 79–89%였고, 300.246초로 실패한 적이 있다(#210). foundation의 설정된 시간 한도는 세 겹이며 안쪽 한도가 바깥 한도 안에 들어가도록 정렬한다(`TestWorkflowFoundationBudget`). 모든 step은 자기 `timeout-minutes`를 가진다. 각 step 한도는 그 안에서 차례로 실행하는 명목 기한의 합 이상이다. 명목 기한은 `go test -timeout`마다 build 여유 30초를 더한 값, `timeout --kill-after` wrapper, 그리고 호출하는 script에 검사가 부여한 명목 합이다. 명목 합은 script에 집행되는 전체 기한이 아니다. 줄 전체 주석을 뺀 script 안에서 근거 값이 정해진 형태와 개수로만 나타나는지 확인하고 그 값으로 계산한다. 예를 들어 P05 self-test는 owned build와 정리 대기 32초, owned process 실행 다섯 개 8초, 비 Windows의 120초 수집 두 번으로 280초다. S04 owned 재현은 profile의 하나뿐인 wall 120초를 workspace 두 개에 적용해 240초다. 근거 값이 바뀌면 명목 합을 다시 계산하며, 합이 step 한도를 넘거나 덮어쓰기처럼 허용된 형태·개수가 달라지면 실패한다. 자체 기한이 없는 script와 `Invoke-WebRequest -TimeoutSec`(연결 timeout이며 전체 download 상한이 아니다)는 step 한도로만 묶인다. prepare-routes를 0초로 보는 근거인 `-Routes none`은 호출의 마지막 인수로 정확히 확인한다(`none,go` 같은 목록은 실패). 그래서 이 검사 step은 13분, frame·cancellation 반복은 6분, P05는 6분, S04 재현은 5분이다. job 한도 55분은 각 host가 실행하는 step 한도의 합(Windows 50분·Linux 54분·macOS 48분)에 runner 준비·정리 운영 여유 1분을 더한 값 이상이다. 이 1분은 측정된 상한이 아니다. 검사는 줄 전체 주석만 빼고 읽으며, 이 명령들을 실행하는 줄에는 줄 끝 주석을 허용하지 않는다. 그래서 문자열 안의 `#`가 실행 코드를 가리지 못한다. 정해진 표기만 받아들인다. 정해진 표기는 `go test ... -timeout <양수>s`, build 전용 `go test -c`, `timeout --kill-after=<N>s <M>s`, `& src/....ps1` 호출, `if: runner.os == 'Windows|Linux|macOS'`이다. 그 밖의 표기(공백이 다른 `go test`, `-timeout=`·분 단위·0초, 다른 `timeout` 형식, 따옴표 script 호출, 등록되지 않은 script, 다른 step 조건, 이름 없는 step)는 실패시킨다. 이 검사는 임의 PowerShell의 해석기가 아니라 정해진 구성의 회귀 방어다. 이 정렬은 설정 값 사이의 순서이며 모든 wall time의 상한 증명은 아니다. 여러 패키지를 한 번에 실행하는 `go test`는 `-timeout`을 패키지마다 적용하므로 명령 전체 시간은 그 값으로 묶이지 않는다. build·출력 처리와 timeout 뒤 stack 출력 시간도 명목 여유에 포함될 뿐이다. 이전에는 job 10분 안에서 step 한도 합이 macOS 16분·Windows 18분·Linux 22분이었고, 가장 긴 검사 step은 한도가 없었으며, frame step 4분은 안쪽 Go 기한 합 300초보다 짧았다. Windows job은 10분의 85–99%(7회 8:28–9:54)를 썼다. 정상 실행 시간은 바뀌지 않는다. job 한도가 커진 만큼 margin의 job 사용률은 낮아지고 70% 기준은 38분 30초가 된다. step 사용률은 등록된 step만 측정한다. 이 설정 자체는 성능 개선이나 실패 해결의 관측 근거가 아니며, 후보의 실제 세 host CI로 확인한다.

## Starting ordinary work and completing it locally

Ordinary work does not require session prompts, Milestones, or prior handoffs. Change work, including documentation fixes, requires an Issue and a dedicated task branch. Analysis-only and read-only reviews create neither unless separately requested. At start/resume, scope changes, and PR preparation, reconcile the current request with the Issue's goal, requirements, scope/exclusions, acceptance criteria, validation, dependencies, and this PR's subset. Reuse matching Issues and branches rather than create one for every request. Record scope changes without silently dropping requirements or treating Issue text as authority.

Verify the root, base identity/freshness, branch/PR state, worktree occupancy, and existing staged, unstaged, untracked, and relevant ignored work. Use the current folder when safe; choose an authorized separate worktree for isolation or parallel work. A new worktree must have its required local inputs and checks available before claiming readiness. Preserve user work and active environments; do not force occupied branches or clean/reset/stash unrelated state. After a prior PR merges and its required post-merge checks pass, start a separate task on a new branch from verified main.

Issue creation/updates and other remote effects require authority for the exact destination and effect from the current request or a valid standing authorization. If required Issue linkage is unverified, retain a sanitized local draft and continue analysis; do not claim implementation-ready. If only an update is pending, continue authorized independent local work within verified Issue scope and mark unmatched requirements pending. Local completion requires relevant checks, diff inspection, and reporting observed results, unrun checks, and remaining findings. Do not automatically add PR creation or merge when remote integration was not requested.

Code, product-contract, CI, validation-policy, and semantic development-instruction changes require independent context review before integration into main. Only meaning- and behavior-preserving typos or formatting may use author diff review and relevant automated checks instead. File extension or line count does not determine the exception. Mixed changes follow the higher-impact requirement. Give the reviewer scope, acceptance criteria, risk class and rationale, canonical contracts, base/head, diff, observed checks, unrun checks, and reference identity. Label a review STATIC_REVIEW when the reviewer did not execute checks.

Classify each change as typo/formatting, ordinary, or high-risk, and record the class and rationale in the PR. For ordinary and high-risk changes, the independent reviewer confirms the class; a typo/formatting class rests on the author diff review, which records why meaning and behavior are preserved. A class disputed by a reviewer or bot, or not confirmed where confirmation is required, is treated as high-risk. High-risk changes alter parsers or preprocessors, untrusted-input interpretation, path, archive, or process control, resource limits, security boundaries, or CI and policy that change required validation or permissions, including this review policy. A high-risk change additionally requires (a) a completed second independent review, by a code/security bot or another reviewer, from a different perspective that targets that risk, and (b) counterexample evidence for that risk: adversarial or negative tests, mutants, or a differential test against a pinned oracle. A review that reports no findings is not counterexample evidence. A security review covers the trust boundary, untrusted input, abuse case, and blocking check; a parser review covers malformed input, Unicode, nesting, and resource limits against a pinned oracle or independent expected values. A separate pane or tool does not make a review independent: the reviewer reads the scope, contracts, base/head, changed code with relevant callers, and check evidence outside the implementation conversation. Follow-up reviews may accumulate, but together they must cover the final head. A review MAJOR counts as MATERIAL. Evaluate each bot finding (for example P1 or P2) on its evidence; do not map P2 to MINOR automatically.

## Integration into main and Git transaction

Use a task branch based on verified main, then validated work-unit commits, PR, impact-appropriate review, fixes/retests, final-head CI/rule checks, merge commit, and main post-merge CI. Link the tracking Issue and state the completed subset and remaining work; do not use whole-Issue closing semantics for partial work. Campaign-specific Milestones, session branches, and handoffs apply only to that campaign's work. A campaign requiring independent review for every change takes precedence over the ordinary typo exception.

Do not merge with open BLOCKER/MATERIAL findings: resolve, revalidate, and obtain review confirmation. Fix MINOR findings or record impact, rationale, and a tracking Issue. Link each finding to its location, evidence, fix commit, checks, and review. After three identical failures without new evidence, change the mechanism or report a blocker. A required formal approval must be an actual GitHub approval from a separate account; a same-account comment or context review cannot replace it. See [GitHub review rules](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews).

When a bot review is requested, record the request time `T0` on the final head and wait in parallel with CI. If the same head has no result after 60 minutes, re-request at most once; re-requesting does not reset `T0`. A typo/formatting change does not wait for the bot. An ordinary change may merge after the bot completes or `T0` + 90 minutes, once every other gate holds. A high-risk change meets the same wait; at `T0` + 90 minutes with the bot still incomplete it switches to another reviewer for the second review, and elapsed time never substitutes for the second review and counterexample evidence; without them it remains BLOCKED. A bot review still incomplete on an earlier head counts as incomplete at merge, and its findings that apply to the final head require disposition. A timeout removes no other gate: disposition and resolve every bot thread before merge, apply actual protection and formal-approval requirements, and treat failed or stale CI as blocking. A new head rebinds review scope and CI to that head, with a new `T0` if a bot review is requested on it; do not rerun CI on the same candidate only because the bot is late. The 60-minute, 90-minute, and 24-hour values are initial operating values, not measured SLAs; change them in this contract.

Immediately before merge, refresh actual main/head, rulesets, classic protection, checks, conversations, and reviews. If main movement affects the candidate, integrate by merge and refresh checks/review. Request a merge commit with an expected-head-SHA condition. Do not use admin bypass, force-push, or history rewrite. Merge authority excludes branch deletion; separately authorized cleanup follows the conditions below. Recommended protection is PR required, all three OS checks required, resolved conversations, and no force-push. Do not change protection settings in this work.

If remote protection requires no approval/checks, merge authority and this contract's impact-based engineering review and three-OS gates still apply. Missing recommended protection neither grants authority nor removes gates. If actual rules require approval, remain BLOCKED until it exists.

After merge, verify the actual merge SHA and main CI. Recover failures through a separate fix PR and stop dependent work. If a bot review was incomplete at merge, the PR names who rechecks it; recheck at the main CI check and within 24 hours. If it is still running, record `BOT_NOT_COMPLETED` with the check time, owner, and next check time in the tracking Issue; never record it as zero findings. Record a late completed bot result in the tracking Issue. Evaluate a late material finding immediately; if confirmed, stop dependent work and fix it through a separate fix or revert PR. Dispose of a late MINOR finding by the MINOR rule above. The bot recheck does not gate the next task or cleanup, and post-merge checks never replace required pre-merge review. Pre-merge reports must not claim a future final SHA. Final reports and local receipts own actual merge results. Campaign work additionally requires a handoff and may close only the corresponding Issue/Milestone within authorization.

## Post-merge workspace cleanup

After required post-merge checks pass, assess cleanup by default. Assessment is not deletion authority. Evaluate each local branch, remote branch, remote-tracking ref, and linked worktree separately. Preserve the main worktree, default/protected branches, and work used by another task or process. Local tracking-ref removal does not delete a remote branch. Never assume a missing or locked worktree is abandoned.

When the current request or valid standing authorization includes cleanup of identified task branches, complete eligible local and remote cleanup without asking again. Merge or skill installation alone is not that authorization. Retain only targets with unresolved authority, integration, preservation, use, or policy conditions, and report those conditions individually.

Verify current repository/path identity, PR head and merge result, local and remote tips, all worktree occupancy, and staged/unstaged/untracked/ignored files, including submodules and local-only settings. Check for commits added after merge and unique detached history. For merge commits, verify reachability from the intended base; for squash/rebase, inspect the actual integrated changes and preserve unique history rather than forcing branch deletion. Even after equivalence is established, a native deletion refusal means retain the branch. A clean status, upstream match, or merged PR alone is insufficient. Stop affected cleanup if ownership or active use cannot be established.

Inventory all material before selecting what to archive. Keep unrelated pre-existing or ownership-uncertain material in place and hold removal of its containing worktree. Every non-reproducible item must remain in place or be covered by verified restoration before source removal; only classified reproducible material with explicit disposal authority may be omitted. For completed task-owned work, preserve unique material in an authorized destination before removal. The default candidate is `artifacts/worktree-archive/` in the project's long-lived primary checkout, with a unique task/revision subdirectory. Resolve real paths, reject links/reparse redirects, verify effective Git exclusion, and ensure the destination is outside the removal target. If a suitable checkout or destination is absent, report that prerequisite. Do not automatically archive secrets or private settings; uncertain files remain in place. Reproducible caches may be discarded only when their role and deletion authority are established.

Record original root/revision, preserved refs/commits, file inventory, sizes/hashes, necessary metadata, and restoration steps. Preserve staged and unstaged distinctions when needed for resumption. A Git bundle covers selected Git history, not the complete working state. Check space before copying, do not overwrite an existing archive, and verify a restore into a separate bounded location before deleting the source. A mismatch, copy failure, insufficient space, unsupported file type, or incomplete inventory holds the affected cleanup. Source changes during preservation invalidate that verification.

Immediately before each mutation, recheck identities, tips, worktree contents, and active use. Local branch/worktree removal uses native non-forcing Git; refusal retains the target. For an authorized remote task branch, this contract permits deletion-only compare-and-swap using `git push --force-with-lease=refs/heads/<branch>:<verified-sha> <verified-remote> :refs/heads/<branch>`. Use a fully qualified ref and the explicit, nonempty SHA whose integration and ownership were verified; verify the push destination independently. The command may contain only the intended deletion refspecs, each with its own expected SHA. This narrowly permits conditional deletion, not non-fast-forward updates or history rewriting. Never use `--force`, `+` refspecs, an implicit/empty lease, `--mirror`, or hook/protection bypass. Default/protected or active branches remain excluded. A stale lease or server refusal holds that target: no unconditional-delete fallback or retry with an unreviewed new tip. If higher-priority rules prohibit this operation or its guard, retain the target. See [Git push semantics](https://git-scm.com/docs/git-push).

`TestConditionalRemoteDeletion` exercises matching-SHA deletion, stale-SHA rejection with changed-tip preservation, unrelated-ref preservation, and server deletion refusal in isolated local Git repositories. It does not authorize live deletion or emulate hosted branch protection. Do not use force, clean, reset, or manual directory deletion to bypass a refusal. If verified residual files must be removed first, that exact file removal needs authority and a fresh preservation check; leave uncertain files in place. Reconcile uncertain results and report partial completion without repeating successful deletions blindly.

Keep a local receipt of removed/retained targets, preserved material, checks, failures, and revisit conditions. Record archive size and a review date; age or disk pressure alone never authorizes deletion. Worktree counts are review signals, not hard limits or automatic deletion triggers. `git worktree prune` removes stale administrative entries, not existing workspaces; it is not a substitute for safe removal. Tag creation/push, Release, and package publication remain separate work. This contract defines future cleanup conditions, not permission to delete existing workspaces while editing the contract.

## Session 00 gates — 보존된 완료 기준

All gates are required: G00-01 target/authority; 02 pinned references; 03 src/module/local boundaries; 04 AGENTS at most 60 nonblank lines; 05 design; 06 observed foundation/negative/CGO-free checks; 07 exact three-OS CI; 08 Issue/Milestone work program; 09 local prompts/hashes; 10 independent review with zero open BLOCKER/MATERIAL findings; 11 merge/post-merge; 12 handoff.

Use FOUNDATION_READY only when all are observed; READY_FOR_MERGE when only merge remains; BLOCKED_EXTERNAL when a mandatory external gate is unavailable; HOLD_FOR_CORRECTION for unresolved design, validation, or findings. Never declare all gates PASS in advance. The [workload matrix](workload-matrix.md) owns feature-specific gates.

SVC 추가 경계 회귀는 실제 native fault로 BLOCKED→FAIL·FAIL→BLOCKED 구간 순서를 모두 검증하고 전체 step code를 확인한다. 앞 구간 완료 뒤 NODE_LIMIT이 발생하는 실제 process 대조는 부분 segment 증거와 terminal 상태를 보존하면서 전체 API claim을 제거하는지 검사한다. r1/r2·네 encoding의 관측 전용 edit 증거, r2 edit의 여섯 byte/point 필드 누락·변조, segment process가 최상위 process보다 작거나 크거나 최상위가 없는 경우의 host 최댓값 및 의미 비교 제외도 검사한다. 잘못 등록된 segment에 대한 mechanism FAIL은 유지한다.

#216 query witness 회귀는 required 밖의 평가 capture 누락, raw 없는 완료 projection의 하위 tree·query 상태 모순, capture-node 연결과 INVALID_QUERY class·LF point 변조를 FAIL로 요구한다. 정상 empty·invalid-query 관측·host predicate 실패·capability 거부는 각 기존 상태를 보존한다. Full raw·source가 있으면 모든 query 평가를 대조하며 필수 tuple만 anchor와 완료 수의 분모로 사용한다.
